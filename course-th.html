โมดูล 01

เริ่มต้น & สิ่งที่จะได้เรียนรู้

ปฐมบทสั้นๆ — ทำไมต้องมี Skill, อะไรเปลี่ยนแปลงเมื่อเริ่มใช้, และเส้นทางของหลักสูตร

Coding Agent สมัยใหม่เก่งงานทั่วๆ ไป แต่มักจะ ไม่มี บริบทเฉพาะที่จำเป็นสำหรับการทำงานจริงให้น่าเชื่อถือ — เช่น convention การ commit ของทีม, วิธีกรอกฟอร์ม PDF ที่บริษัทใช้, runbook การ migrate ที่ Senior Engineer เก็บไว้ใน Notion. Agent Skill คือฟอร์แมตเปิดสำหรับเก็บความรู้เชิงขั้นตอนเหล่านั้นในรูปโฟลเดอร์ (มี SKILL.md หนึ่งไฟล์ บวกพี่น้องเลือกได้) ซึ่ง agent ทุกตัวที่รองรับมาตรฐานสามารถค้นเจอและโหลดเข้าใช้งานเมื่อต้องการ

เมื่อเขียน Skill ครั้งเดียว — เราเลิกพิมพ์คำสั่งเดิมๆ ทุก session. เมื่อมันเข้า source control — ทั้งทีมได้ใช้. เมื่อมันอยู่ใน .agents/skills/ — ทุก client ที่รองรับมาตรฐาน เช่น Claude Code, Copilot, Cursor, Codex, Gemini CLI และอีกหลายสิบตัว — สามารถใช้งานได้โดยไม่ต้องดัดแปลง

หัวข้อที่ครอบคลุม

  • โครงสร้างทางเทคนิคของ Skill — frontmatter, body, ไฟล์พี่น้อง, กฎ validation
  • Progressive disclosure — ทำไม Skill ไม่ทำให้ context window ระเบิด และวิธีเขียนให้ใช้ประโยชน์
  • มาตรฐานเปิดที่ agentskills.io และ convention ข้าม client
  • กรอบการตัดสินใจระหว่าง Skill / MCP / Subagent (จะต้องใช้ทั้ง 3 อย่าง)
  • แนวปฏิบัติการเขียนพร้อมตัวอย่างจริง
  • Lab สั้นๆ เรื่องการปรับ description — มิติคุณภาพที่สำคัญที่สุด
  • วิธีทำ client ของคุณเองให้รองรับ Skill
  • โมเดลความปลอดภัย, แผน roll-out, และ cheatsheet ที่เก็บไว้ใช้ต่อได้

ใช้เวลา

~45 นาทีสำหรับการอ่าน, ~90 นาทีถ้าทำ Lab ด้วย

โมดูล 02

Agent Skill คืออะไร

นิยามที่ชัดเจน ไม่ผูกกับเจ้าใดเจ้าหนึ่ง

Agent Skill คือโฟลเดอร์ที่จัดระเบียบไว้ ประกอบด้วยคำสั่ง สคริปต์ และทรัพยากรต่างๆ ซึ่ง agent สามารถ ค้นหาและโหลดเข้ามาแบบ dynamic เพื่อทำงานเฉพาะอย่างให้ดีขึ้น สัญญาของรูปแบบนี้มี 3 ส่วน:

  1. โฟลเดอร์ ที่ชื่อตรงกับชื่อ Skill
  2. ไฟล์ SKILL.md ที่ root ของโฟลเดอร์ มี YAML frontmatter + markdown
  3. โฟลเดอร์พี่น้องแบบทางเลือก ตามชื่อมาตรฐาน: scripts/, references/, assets/
my-skill/
├── SKILL.md          # บังคับ — ไฟล์เริ่มต้น
├── scripts/          # ทางเลือก — โค้ดที่รันได้
├── references/       # ทางเลือก — เอกสาร
├── assets/           # ทางเลือก — template, ข้อมูล
└── ...

สเปคถูกออกแบบให้น้อยที่สุดเท่าที่จำเป็น มีฟิลด์บังคับ 2 ตัว — name และ description — บวก markdown body. ส่วนอื่นเป็น optional หรือเฉพาะ platform

"การสร้าง Skill ก็เหมือนการเขียนคู่มือต้อนรับพนักงานใหม่" — Anthropic Engineering

การเปรียบเทียบนี้แม่นยำ — พนักงานใหม่ไม่ต้องท่องทั้ง wiki ในวันแรก เขาต้องการสารบัญและ pointer ไปยังเอกสารลึกๆ. Agent ก็เหมือนกัน — มันไม่อ่าน Skill ทุกตัวจนจบ มันอ่านเฉพาะตัวที่เห็นว่าตรงกับงานปัจจุบัน

ใจความสำคัญ

Skill เป็น โฟลเดอร์ ไม่ใช่ snippet. โครงสร้างไฟล์นั่นแหละ คือสิ่งที่ทำให้ progressive disclosure เป็นไปได้

โมดูล 03

โครงสร้างของ SKILL.md

ฟิลด์ใน frontmatter, กฎ validation และเนื้อหา body

ทุกไฟล์ SKILL.md เริ่มด้วย YAML frontmatter ที่ขนาบด้วย ---:

---
name: pdf-processing
description: Extract text and tables from PDF files, fill forms, merge documents. Use when working with PDF files or when the user mentions PDFs, forms, or document extraction.
---

# PDF Processing
...เนื้อหา markdown...

ฟิลด์บังคับ (ตามมาตรฐานเปิด)

ฟิลด์กฎ
name1-64 ตัวอักษร · ตัวพิมพ์เล็ก/ตัวเลข/ขีดกลาง · ห้ามขึ้นหรือลงด้วย - · ห้าม -- ติดกัน · ต้องตรงกับชื่อโฟลเดอร์แม่
description1-1024 ตัวอักษร · ต้องบอกทั้ง ทำอะไร และ ใช้เมื่อไหร่

ฟิลด์ทางเลือก (ตามมาตรฐานเปิด)

ฟิลด์ใช้ทำอะไร
licenseชื่อ License หรือชื่อไฟล์ License ที่ bundle มาด้วย
compatibility≤500 ตัวอักษร · ระบุข้อกำหนดสภาพแวดล้อม เช่น Requires Python 3.14+ and uv
metadatamap string→string สำหรับฟิลด์เพิ่มเติมที่ client กำหนดเอง (เช่น version, author)
allowed-toolsรายการ tool ที่ pre-approve คั่นด้วย space — ยังเป็น Experimental

ฟิลด์เสริมเฉพาะ Claude Code

Claude Code เพิ่มฟิลด์ที่ใช้ได้เฉพาะตอน Skill ทำงานใน Claude Code: when_to_use, argument-hint, arguments, disable-model-invocation, user-invocable, model, effort, context: fork, agent, hooks, paths, shell — ใช้เมื่อต้องการพฤติกรรมเฉพาะ ถ้าต้องการ portability ข้าม client ให้ยึดเฉพาะฟิลด์มาตรฐาน

เนื้อหา (Body)

เขียนอะไรก็ได้ที่ช่วย agent ทำงานได้ดี — ขั้นตอน, ตัวอย่าง, edge case. ไม่มีข้อจำกัดเรื่องฟอร์แมต. ที่แนะนำคือไม่เกิน 500 บรรทัด — ถ้าเกินให้แตกเป็นไฟล์พี่น้อง

ใจความสำคัญ

มาตรฐานเล็กโดยเจตนา — ใช้ฟิลด์บังคับให้คล่องก่อน แล้วค่อยเพิ่มฟิลด์ทางเลือกเมื่อจำเป็นจริงๆ

โมดูล 04

Progressive Disclosure

หลักการออกแบบเดียวที่ทำให้ Skill ขยายได้ไม่จำกัด

ถ้า Skill ทุกตัวถูกโหลดทั้งเนื้อหาเข้า context ตั้งแต่ตอน startup, การติดตั้ง 10 Skill ก็จะเผา 50,000 token ก่อนผู้ใช้พิมพ์อะไรเลย. Progressive disclosure คือโมเดลการโหลดทีละขั้นที่ป้องกันปัญหานี้ — Skill จะถูกโหลดใน 3 ระดับ:

ระดับโหลดอะไรเมื่อไหร่Token ที่ใช้
L1 — Metadataname + descriptionตลอด (เริ่ม session)~100 / Skill
L2 — InstructionsSKILL.md bodyเมื่อ agent ตัดสินใจว่าตรงงาน< 5,000 (แนะนำ)
L3+ — Resourcesไฟล์ใน scripts/, references/, assets/เรียกตามต้องการผ่าน bash / file-readเกือบไม่จำกัด

L3 คือจุดที่กำลังขยายตัว ไฟล์อ้างอิงเช่น references/finance.md กิน 0 token จนกว่า agent จะเปิดดู. สคริปต์ยิ่งดีกว่า — โค้ดต้นฉบับไม่เคยเข้า context มีแต่ output เท่านั้น. สคริปต์ Python 2,000 บรรทัดที่พิมพ์ "OK" ใช้แค่ 3 token

ผลต่อการเขียน

  • SKILL.md body ไม่ควรเกิน 500 บรรทัด — เนื้อหาที่ใหญ่กว่าให้แตกเป็นไฟล์พี่น้อง
  • อ้างอิงไฟล์พี่น้อง ลึกแค่ระดับเดียว จาก SKILL.md — agent อาจอ่านไฟล์ที่ต่อกันแบบ partial (เช่น head -100) ทำให้พลาดเนื้อหาหลังบรรทัด 100
  • ไฟล์อ้างอิงที่ยาวกว่า ~100 บรรทัด ต้องมี Contents อยู่ด้านบน เพื่อให้ agent กระโดดไปส่วนที่ต้องการได้
  • งาน deterministic ที่รันยาว ให้เขียนเป็น script ดีกว่าการเขียน instruction ให้ agent ทำตามเป๊ะๆ

Pattern 1 — guide + references

# PDF Processing

## Quick start
[คำแนะนำ inline สั้นๆ]

## Advanced features
- Form filling: see [FORMS.md](FORMS.md)
- Reference: see [REFERENCE.md](REFERENCE.md)
- Examples: see [EXAMPLES.md](EXAMPLES.md)

Pattern 2 — แยกตามโดเมน

Skill ที่มีหลายโดเมน เช่น BigQuery ที่มีหลาย dataset ให้แยกอ้างอิงตามโดเมน เพื่อ agent โหลดเฉพาะที่ถูกถาม:

bigquery-skill/
├── SKILL.md
└── reference/
    ├── finance.md   # revenue, billing
    ├── sales.md     # pipeline, opportunities
    ├── product.md   # adoption, usage
    └── marketing.md # attribution

ใจความสำคัญ

คุณติดตั้ง Skill ได้เป็นสิบเป็นร้อยตัว ตราบใดที่แต่ละตัวถูกออกแบบสำหรับ progressive disclosure. คอขวดคือ description ไม่ใช่ body

โมดูล 05

เป็น Open Standard ไม่ใช่ของ Anthropic เท่านั้น

ทำไม Skill ถึง portable และมาตรฐานทางการอยู่ที่ไหน

Anthropic เป็นคนคิดฟอร์แมต SKILL.md ก่อน แล้วปล่อยเป็น open standard ที่ agentskills.io โดยใช้ GitHub repository สาธารณะ เป็นที่กำกับดูแล. มาตรฐานกำหนดเฉพาะ ฟอร์แมต — ส่วนการโหลดและการรันแล้วแต่ client

ณ พฤษภาคม 2569 ฟอร์แมตนี้ได้รับการรองรับโดย ecosystem ข้ามค่ายอย่างกว้างขวาง:

Claude Code · Claude.ai · GitHub Copilot · VS Code · OpenAI Codex · Cursor · Gemini CLI · OpenCode · OpenHands · Goose (Block) · Letta · Roo Code · Mistral Vibe · Snowflake Cortex Code · Databricks Genie · Spring AI · Laravel Boost · Kiro · Factory · Junie (JetBrains) · Amp · Mux · Ona · Workshop · Trae (ByteDance) · Piebald · Pi · Emdash · Qodo · VT Code · Command Code · Agentman · Firebender · Google AI Edge Gallery · nanobot · fast-agent · Autohand

ไฟล์ SKILL.md เพียงหนึ่งไฟล์ เขียนครั้งเดียว ใช้ได้กับทุกเครื่องมือข้างต้นโดยไม่ต้องแก้ — ตราบใดที่คุณใช้ฟิลด์ frontmatter ในกลุ่มมาตรฐาน และไม่พึ่งฟีเจอร์เฉพาะ client. นี่คือคุณค่าของ open spec — เขียนครั้งเดียว ใช้ได้ทั่ว ecosystem

Convention ข้าม client: .agents/skills/

มาตรฐาน ไม่ได้ บังคับว่า Skill ต้องอยู่ที่ไหน แต่ ecosystem มาบรรจบกันที่ .agents/skills/ เป็น path กลาง — client ที่รองรับมาตรฐานควรสแกนตำแหน่งนี้ นอกเหนือจาก path ของ client เอง

ขอบเขตเฉพาะ clientข้าม client
Project<repo>/.<client>/skills/<repo>/.agents/skills/
User~/.<client>/skills/~/.agents/skills/

กฎสากล: Project ทับ User. Client ใหม่ๆ หลายตัวยังสแกน .claude/skills/ เพื่อความเข้ากันด้วย เพราะ Skill เก่าจำนวนมากอยู่ที่นั่น

ใจความสำคัญ

วาง Skill ของทีมไว้ที่ <repo>/.agents/skills/ · ของส่วนตัวที่ ~/.agents/skills/ · ใช้ path เฉพาะ client เมื่อจำเป็นต้องใช้ฟิลด์เฉพาะ client เท่านั้น

รายละเอียด Claude API

Skill รันใน sandbox code-execution ของ API. ต้องการ beta header 3 ตัว:

anthropic-beta: code-execution-2025-08-25
anthropic-beta: skills-2025-10-02
anthropic-beta: files-api-2025-04-14

อ้างอิง Skill ผ่าน skill_id ใน parameter container ร่วมกับ tool code-execution. Sandbox ไม่มีเครือข่าย และ ติดตั้ง package ตอน runtime ไม่ได้ — ใช้ได้เฉพาะ package ที่ติดมาแล้ว. Skill ยัง ไม่ รองรับ Zero-Data-Retention

รายละเอียด Claude Code

ตำแหน่งและลำดับ:

ที่ตั้งPathขอบเขต
Enterprisemanaged settingsทั้งองค์กร
Personal~/.claude/skills/<ชื่อ>/SKILL.mdทุกโปรเจกต์ของคุณ
Project.claude/skills/<ชื่อ>/SKILL.mdเฉพาะ repo นี้
Plugin<plugin>/skills/<ชื่อ>/SKILL.mdเมื่อเปิดใช้ plugin

ลำดับ: enterprise > personal > project. Plugin skill ใช้ namespace plugin:skill ไม่ชนกัน

Superpowers ของ Claude Code

  • !`git diff HEAD` — Dynamic Context Injection: รัน shell ก่อน Claude อ่าน Skill output แทรกในข้อความ
  • context: fork — รัน Skill ใน subagent ที่มี tool และ context แยกออกจากบทสนทนาหลัก
  • allowed-tools — pre-approve tool ตอน Skill ทำงาน ข้ามการ confirm รายครั้ง
  • disable-model-invocation: true — เฉพาะ user เท่านั้นที่กดเรียกได้ (ใช้สำหรับ /deploy, /send-slack)
  • ${CLAUDE_SKILL_DIR} — ชี้ไปยังโฟลเดอร์ของ Skill เอง · ทำให้ script bundle ทำงานได้ไม่ขึ้นกับ working directory

หมายเหตุข้าม Surface

Custom Skill ไม่ sync ข้าม surface ต้องอัปโหลดแยกที่ API, claude.ai, Claude Code. ที่ portable คือ ฟอร์แมต ไม่ใช่ deployment

โมดูล 07

Skill vs MCP vs Subagent

3 คำถามที่ต่างกัน ไม่ใช่ 3 คำตอบที่แข่งกัน

มือใหม่มักพยายามเลือกเอาตัวเดียว แต่ระบบ production มักใช้ทั้ง 3 อย่าง. กุญแจคือรู้ว่าแต่ละอย่างเก่งงานแบบไหน

คุณสมบัติSkillPromptProjectSubagentMCP
วัตถุประสงค์ความรู้เชิงขั้นตอนคำสั่งราย turnความรู้พื้นหลังมอบหมายงานเชื่อมต่อ tool ภายนอก
คงอยู่ข้ามบทสนทนาบทสนทนาเดียวใน projectข้าม sessionต่อเนื่อง
การโหลดDynamic ตามต้องการทุก turnโหลดเสมอเมื่อเรียกมีอยู่ตลอด
มีโค้ดได้มีไม่มีไม่มีมีมี

กรอบการตัดสินใจ

ต้องการให้ Claude รู้วิธีทำ X ซ้ำๆ?         → Skill
ต้องการให้ Claude เข้าถึงระบบภายนอก?       → MCP
ต้องการงานที่ทำแยก มี context ของตัวเอง?   → Subagent

การ Compose (pattern ทรงพลังที่สุด)

main agent
  └─ subagent: code-reviewer (มี context แยก, tool อ่านอย่างเดียว)
       └─ skill: review-conventions (โหลดตอนใช้งาน)
              └─ MCP: GitHub (ดึง diff + comment ของ PR)

ทุกชั้นมีเหตุผลของตัวเอง — Subagent แยก context, Skill ถือ know-how, MCP ดึงข้อมูล. งานสำคัญเกิดที่จุดเชื่อมต่อระหว่างทั้งสาม

ใจความสำคัญ

อย่ามองเป็น either/or — คำตอบที่ถูกมักเป็น "Skill บวก MCP, อาจอยู่ใน Subagent ด้วย"

โมดูล 08

แนวปฏิบัติในการเขียน Skill

คำแนะนำทางการของ Anthropic แบบกลั่น

4 หลักการสำคัญ

  1. กระชับ — context window คือทรัพย์สินส่วนรวม ทุก token หลังโหลด SKILL.md จะแย่งพื้นที่กับบทสนทนา
  2. ถือว่า Claude ฉลาด — เพิ่มเฉพาะสิ่งที่โมเดลยังไม่รู้ ไม่ต้องอธิบายว่า PDF คืออะไร
  3. ปรับระดับอิสระให้เหมาะกับงาน — DB migration ต้องการคำสั่งเป๊ะ; code review ต้องการแค่ทิศทางทั่วไป
  4. ทดสอบกับทุกโมเดล ที่ Skill จะใช้ (Haiku, Sonnet, Opus) — ที่ใช้กับ Opus ดี อาจต้องบอกละเอียดกว่ากับ Haiku

การตั้งชื่อ

ใช้รูป gerund (verb + ing) ถ้าเป็นไปได้: processing-pdfs, analyzing-spreadsheets, reviewing-pull-requests. หลีกเลี่ยงชื่อกว้างๆ — helper, utils, tools, data — ไม่บอก agent ว่าจะใช้ เมื่อไหร่

กฎของ Description

  • เขียนด้วย บุรุษที่สามเสมอ — "Processes Excel files…", ห้ามเขียน "I can help…" หรือ "You can use this…"
  • ต้องบอกทั้ง ทำอะไร และ เมื่อไหร่
  • ใช้ประโยคคำสั่งสำหรับส่วน trigger: "Use when the user…"
  • "Err on the side of being pushy" — ระบุบริบทใกล้เคียง: "…even if they don't explicitly mention CSV or analysis."

Anti-patterns ที่ต้องเลี่ยง

  • Path แบบ Windows (scripts\helper.py) — ใช้ forward slash เท่านั้น
  • Voodoo constants — ทุกตัวเลขลึกลับต้องมีคำอธิบาย ไม่งั้นเป็นบั๊กที่รออยู่
  • "Punt-to-Claude" error handling — แก้ใน script ไม่ใช่โยนปัญหากลับใส่ prompt
  • เสนอทางเลือก 3-4 ทาง — ให้ default 1 ตัว + ทางลงเสริม
  • คำสั่งที่ผูกกับเวลา — ของเก่าให้ย้ายไปส่วน "Legacy" จะได้ไม่กระทบของใหม่

Workflow

สำหรับงานหลายขั้น ให้ checklist ที่ agent คัดลอกใส่ response แล้วติ๊กตามไปได้. Pattern: plan → validate → execute — ขั้น validate ดักจุดผิดก่อนจะกลายเป็นความเสียหาย

## ขั้นตอนกรอกฟอร์ม PDF

คัดลอก checklist:
- [ ] ขั้น 1: วิเคราะห์ฟอร์ม (รัน analyze_form.py)
- [ ] ขั้น 2: สร้าง field mapping (แก้ fields.json)
- [ ] ขั้น 3: ตรวจ mapping (รัน validate_fields.py)
- [ ] ขั้น 4: กรอกฟอร์ม (รัน fill_form.py)
- [ ] ขั้น 5: ยืนยันผลลัพธ์ (รัน verify_output.py)

ใจความสำคัญ

2 จุดที่ leverage สูงสุดในทุก Skill คือ description (ทริกเกอร์ถูกเวลามั้ย) และ workflow (ทำให้พลาดยากขึ้นมั้ย) — อื่นๆ รองลงมาทั้งหมด

โมดูล 09

Lab — ปรับ Description

Lab สั้นๆ — ปรับ description ของ Skill เหมือนปรับโมเดล ML

ฟิลด์ description เป็น ปุ่ม trigger เพียงปุ่มเดียว — ระบุไม่ชัดก็ไม่ activate, กว้างเกินก็ activate ผิดเวลา. agentskills.io เผยแพร่ loop ที่ยืมแนวคิดจาก ML evaluation

ขั้นที่ 1 — เตรียม query set ที่ติด label

ตั้งเป้า 20 query แบบที่ user จริงพิมพ์: should-trigger ครึ่ง, should-not ครึ่ง

[
  { "query": "I've got a spreadsheet in ~/data/q4_results.xlsx with revenue in col C and expenses in col D — can you add a profit margin column and highlight anything under 10%?", "should_trigger": true },
  { "query": "whats the quickest way to convert this json file to yaml", "should_trigger": false }
]

Should-trigger query ให้หลากหลายในแกน: phrasing (ทางการ/casual/พิมพ์ผิด), explicitness (เอ่ยชื่อโดเมนกับซ่อน), detail (สั้นกับยาว), complexity (ขั้นเดียวกับหลายขั้น)

Should-not query ที่มีค่าที่สุดคือ near-miss — query ที่มี keyword ทับซ้อนกับ Skill แต่จริงๆ ต้องการสิ่งอื่น. "Write a fibonacci function" เป็น negative ที่อ่อน (ไม่ทดสอบอะไร); "I need to update the formulas in my Excel budget spreadsheet" เป็น negative ที่แข็งแกร่งสำหรับ skill วิเคราะห์ CSV เพราะ keyword ทับ แต่งานจริงคือแก้ Excel ไม่ใช่วิเคราะห์ CSV

ขั้นที่ 2 — แบ่ง train / validation

Train ~60% · Validation ~40% · ค้างการแบ่งไว้ตลอด เพื่อเปรียบเทียบรอบต่อรอบได้แบบเหมือนๆ กัน. ทั้ง 2 set ต้องมีสัดส่วน positive/negative ใกล้เคียงกัน

ขั้นที่ 3 — วัด trigger rate

โมเดลไม่ deterministic. รันแต่ละ query 3 ครั้ง คำนวณ trigger rate (สัดส่วนรอบที่ Skill ทริกเกอร์). Should-trigger query ผ่านถ้า trigger_rate > 0.5; should-not ผ่านถ้า trigger_rate < 0.5

ขั้นที่ 4 — Iterate

  1. Evaluate ทั้ง train + validation
  2. เลือกดูเฉพาะที่ฟัน train
  3. ปรับ:
    • Should-trigger ฟัน → ขยาย scope, เพิ่มบริบทใกล้เคียง
    • Should-not ฟัน → เพิ่มความเฉพาะเจาะจง, ระบุว่าไม่รวมอะไร
    • อย่าลอก keyword จาก query ที่ฟันมาตรงๆ — นั่นคือ overfit. ให้หาหมวดหมู่ใต้ query นั้นแทน
    • คุมความยาวไม่เกิน 1024 ตัวอักษร
  4. ทำซ้ำประมาณ 5 รอบ
  5. เลือกรอบที่ validation pass-rate ดีที่สุด — ไม่ใช่รอบล่าสุด เพราะรอบเก่าๆ บางครั้งทั่วไปกว่า

ตัวอย่าง ก่อน / หลัง

# ก่อน
description: Process CSV files.

# หลัง
description: >
  Analyze CSV and tabular data files — compute summary statistics,
  add derived columns, generate charts, and clean messy data. Use this
  skill when the user has a CSV, TSV, or Excel file and wants to
  explore, transform, or visualize the data, even if they don't
  explicitly mention "CSV" or "analysis."

"หลัง" เฉพาะเจาะจงในส่วน ทำอะไร (สถิติสรุป, เพิ่มคอลัมน์, ทำชาร์ต, clean ข้อมูล) และ กว้างในส่วน เมื่อไหร่ (CSV/TSV/Excel แม้ไม่เอ่ยคำเหล่านั้น)

Lab — ลองทำตอนนี้

เลือก Skill ใดก็ได้ใน ~/.claude/skills/ (หรือเขียนใหม่), เตรียม query set 20 ตัวที่ติด label, แล้วรัน loop. ถ้าไม่อยากเขียน runner เอง — มี Skill ชื่อ skill-creator ใน anthropics/skills ที่ทำ loop ทั้งหมดให้พร้อม HTML report

โมดูล 10

สร้าง Client ที่รองรับ Skill

สำหรับคนสร้าง agent ที่อยากให้ตัวเอง conformant กับ Skill มาตรฐาน

โมดูลนี้สำหรับ คนสร้าง agent ไม่ใช่คนเขียน Skill. agentskills.io ตีพิมพ์ lifecycle 5 ขั้นตอน — ตั้งแต่สแกน filesystem จนถึงดูแล context

ขั้น 1 — Discover

สแกน scope project + user (และเลือกได้ org/built-in) หา subdirectory ที่มีไฟล์ SKILL.md เป๊ะๆ. รวม convention .agents/skills/ เสมอ. หลายตัวสแกน .claude/skills/ ด้วยเพื่อความเข้ากัน

คุมความลึก: depth 4-6, ไม่เกิน ~2,000 directory. ข้าม .git/, node_modules/. เคารพ .gitignore. ตรวจ trust ของ workspace ก่อนโหลด project skill — เพราะมาจาก repo ที่อาจไม่น่าเชื่อถือ

ขั้น 2 — Parse

เป็น lenient — เตือนเฉพาะข้อผิดพลาดเล็ก (name ไม่ตรงโฟลเดอร์, ยาวเกิน 64), ข้าม Skill เฉพาะถ้าเรื่องสำคัญ (description ขาด, YAML พัง). Skill ที่เขียนมาจาก client อื่นบางทีมี YAML ที่เพี้ยนเล็กน้อย — ที่พบบ่อยคือ colon ที่ไม่ใส่ quote ใน value:

description: Use this skill when: the user asks about PDFs   # YAML ไม่ valid

Workaround ที่นิยม: ลอง wrap value ใน quote แล้ว parse ใหม่

ขั้น 3 — Disclose (Tier 1)

แทรก catalog เป็น structured ลงใน system prompt หรือ description ของ tool พิเศษ:

<available_skills>
  <skill>
    <name>pdf-processing</name>
    <description>Extract PDF text, fill forms, merge files. Use when handling PDFs.</description>
    <location>/home/user/.agents/skills/pdf-processing/SKILL.md</location>
  </skill>
</available_skills>

~50–100 token ต่อ Skill. Skill ที่ปิดอยู่ให้ซ่อนทั้งหมด — ไม่ต้องลิสต์แล้วบล็อกตอน activate (เปลืองรอบ)

ขั้น 4 — Activate (Tier 2)

มี 2 แบบ: file-read activation (โมเดลใช้ tool อ่านไฟล์ทั่วไปอ่าน SKILL.md) หรือ tool พิเศษ activate_skill(name). แบบหลังทำให้คุณ wrap content ด้วย tag, ลิสต์ resource ที่ bundle ไว้, และบังคับ permission ได้

จำกัด parameter name ให้เป็น enum ของ Skill ที่ค้นเจอ — กัน hallucinate ชื่อ Skill ที่ไม่มีอยู่

ขั้น 5 — ดูแล context ของ Skill

  • ป้องกัน skill content จากการ compact — สูญหายกลางทาง = พฤติกรรมแย่ลงเงียบๆ ไม่มี error
  • De-duplicate การ activate — ถ้าอยู่ใน context แล้วอย่าฉีดซ้ำ
  • Subagent delegation (advanced) — รัน skill แยก session แล้วคืนแค่ summary

Reference SDK

ใช้ skills-ref เป็น validator + parser. วางใน CI:

skills-ref validate ./my-skill

ใจความสำคัญ

การทำ lifecycle 5 ขั้นให้ถูกต้อง คือสิ่งที่ทำให้คุณเป็น conformant client. ที่ยากที่สุดคือ context management (ขั้น 5) — ทำพลาดแล้ว Skill จะ "หยุดทำงาน" หลัง compaction ครั้งแรกโดยไม่มี error

โมดูล 11

ความปลอดภัย & แผน Roll-out

การติดตั้ง Skill = การติดตั้งซอฟต์แวร์ ต้องระวังเท่ากัน

Threat model

  • คำสั่งที่เป็นพิษ redirect การใช้ tool ไปจากวัตถุประสงค์
  • Script ใน skill อาจ exfiltrate ข้อมูลหรือโจมตี host
  • การ fetch URL ภายนอกใน skill อาจถูก tamper หลังติดตั้ง
  • Skill ที่มี allowed-tools กว้างๆ จะยกระดับ trust boundary แบบเงียบๆ

มาตรการลดความเสี่ยง

  • ติดตั้งจาก แหล่งที่เชื่อถือได้ เท่านั้น — ของ Anthropic หรือของในองค์กร
  • ตรวจ ทุกไฟล์ ใน skill: SKILL.md, references, scripts, asset
  • ระวังเป็นพิเศษถ้า skill ดึง URL ภายนอก ตอน runtime
  • ใน Claude Code: allowed-tools ของ project skill ทำงานเฉพาะหลัง trust workspace แล้ว
  • ใช้ disable-model-invocation: true สำหรับคำสั่งที่มีผลข้างเคียง (/deploy, /send-slack) — trigger ต้องเป็นมนุษย์
  • Claude API ไม่มีเครือข่าย — ลด exfiltration ได้บางส่วน. Claude.ai ขึ้นกับ policy ของ admin

Playbook สำหรับทีม

  1. เลือก workflow 1 เรื่อง ที่ทีมต้องอธิบายซ้ำๆ
  2. เขียน 3 evaluation ก่อน เริ่ม SKILL.md
  3. ร่าง SKILL.md ขั้นต่ำ (ไม่เกิน 100 บรรทัด)
  4. ลองส่วนตัว (~/.claude/skills/ หรือ ~/.agents/skills/) — วน eval
  5. ย้ายไปที่ project (.claude/skills/ หรือ .agents/skills/) — commit เข้า repo
  6. เก็บข้อมูลการใช้งาน 2 สัปดาห์ — รวบรวม case ที่พลาด
  7. สรุปบทเรียนเข้า wiki — ขยายเป็น plugin หากต้องแชร์ทั้งองค์กร

หมายเหตุ ZDR

Skill ยังไม่ รองรับ ZDR ในเดือน พฤษภาคม 2569 อย่าใส่ความรู้ที่ sensitive มากๆ เข้าไปใน skill ที่รันบน surface ที่ไม่ใช่ self-host

Checklist คุณภาพ Skill

คุณภาพหลัก

  • ☐ Description: บุรุษที่สาม, ทำอะไร + เมื่อไหร่, มีคำสำคัญ, <1024 ตัวอักษร
  • ☐ name ตรงกับชื่อโฟลเดอร์ และตามกฎการตั้งชื่อ
  • ☐ SKILL.md body < 500 บรรทัด
  • ☐ ไฟล์อ้างอิงพี่น้องลึกแค่ระดับเดียว
  • ☐ ไฟล์อ้างอิง > 100 บรรทัด มี Contents block
  • ☐ คำศัพท์สม่ำเสมอ
  • ☐ ตัวอย่างเป็นรูปธรรม ไม่นามธรรม
  • ☐ Workflow มีขั้นตอนชัดและเรียงเลข
  • ☐ เนื้อหาที่ผูกกับเวลา ย้ายไปส่วน Legacy

โค้ด & สคริปต์

  • ☐ สคริปต์จัดการ error เอง ไม่ "punt to Claude"
  • ☐ ไม่มี voodoo constant — ทุกตัวเลขมีคำอธิบาย
  • ☐ ใช้ forward slash อย่างเดียว
  • ☐ ระบุ package ที่ต้องใช้ และยืนยันว่ามีใน runtime
  • ☐ มีขั้น validation สำหรับการกระทำที่ destructive
  • ☐ ใช้ pattern plan-validate-execute สำหรับ batch operation

การทดสอบ

  • ☐ Evaluation ≥ 3 ครอบคลุมช่องว่างเดิม
  • ☐ ปรับ description ด้วย train/validation split
  • ☐ ทดสอบบน Haiku / Sonnet / Opus
  • ☐ ผ่าน skills-ref validate
  • ☐ รับ feedback จากทีมแล้ว
