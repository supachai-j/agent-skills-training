นิยาม

Agent Skill คือ โฟลเดอร์ ที่จัดระเบียบไว้ ประกอบด้วยคำสั่ง สคริปต์ และทรัพยากรต่างๆ ที่ agent สามารถ ค้นพบและโหลดเข้ามาแบบ dynamic เพื่อทำงานเฉพาะอย่างให้ดีขึ้น

  • ไฟล์เริ่มต้น: SKILL.md (YAML frontmatter + markdown)
  • โฟลเดอร์พี่น้อง (ตามแบบมาตรฐาน): scripts/, references/, assets/
  • เป็น Open Standard ที่ agentskills.io — Apache 2.0 / CC-BY-4.0

เป็น Open Standard ไม่ใช่ฟีเจอร์เฉพาะ Anthropic

Anthropic เขียนสเปคเริ่มแรก แล้วปล่อยเป็น open standard ผ่าน GitHub ให้ทุกค่ายร่วมพัฒนาได้

ไฟล์ SKILL.md เพียงไฟล์เดียว ใช้ได้กับเครื่องมือต่อไปนี้ (พฤษภาคม 2569 — บางส่วน):

Claude Code · Claude.ai · GitHub Copilot · VS Code · OpenAI Codex · Cursor · Gemini CLI · OpenCode · OpenHands · Goose · Letta · Roo Code · Mistral Vibe · Snowflake Cortex Code · Databricks Genie · Spring AI · Laravel Boost · Kiro · Factory · Junie · Amp · Mux · Ona · Workshop · Trae · Piebald · Pi · Emdash · Qodo · VT Code · Command Code · Agentman · Firebender · Google AI Edge Gallery · nanobot · fast-agent · Autohand

โครงสร้างไฟล์ของ Skill (Anatomy)

my-skill/
├── SKILL.md            # บังคับ — entrypoint
├── reference.md        # โหลดเฉพาะตอนจำเป็น
├── examples.md         # เช่นเดียวกัน
└── scripts/
    └── helper.py       # รันผ่าน bash; โค้ดต้นฉบับไม่เข้า context

แต่ละไฟล์มี "เวลาโหลด" ที่ต่างกัน — และนั่นคือกุญแจสำคัญ

ตัวอย่าง SKILL.md ที่เล็กที่สุด

---
name: pdf-processing
description: Extract text and tables from PDF files, fill forms,
  merge documents. Use when working with PDF files or when the
  user mentions PDFs, forms, or document extraction.
---

# PDF Processing
ใช้ pdfplumber สำหรับการดึงข้อความ:

```python
import pdfplumber
with pdfplumber.open("file.pdf") as pdf:
    text = pdf.pages[0].extract_text()
```

บังคับใส่: name, description — นอกนั้นเป็น body หรือไฟล์ประกอบ

Frontmatter — ฟิลด์บังคับ

ฟิลด์กฎ
name≤ 64 ตัวอักษร · ตัวพิมพ์เล็ก + ตัวเลข + ขีดกลาง · ห้ามขึ้น/ลงด้วย - · ห้าม -- · ต้องตรงกับชื่อโฟลเดอร์
descriptionห้ามว่าง · ≤ 1024 ตัวอักษร · บุรุษที่สาม · บอก ทำอะไร และ ใช้เมื่อไหร่

ฟิลด์ ทางเลือก ของ Open Standard:

license · compatibility (≤500 ตัวอักษร เช่น "Requires Python 3.14+ and uv") · metadata (map string→string) · allowed-tools (experimental)

ฟิลด์เสริมของ Claude Code

เพิ่มเติมจาก spec กลาง:

when_to_use · argument-hint · arguments · disable-model-invocation · user-invocable · allowed-tools · model · effort · context: fork · agent · hooks · paths · shell

ใช้ได้เมื่อต้องการพฤติกรรมเฉพาะของ Claude Code · ถ้าต้องการ portability ข้าม client ให้ยึดเฉพาะฟิลด์มาตรฐาน

Progressive Disclosure (เปิดเผยทีละชั้น)

ไอเดียสำคัญที่ทำให้ติดตั้ง Skill ได้ หลายร้อยตัว โดยไม่ทำให้ context window ระเบิด

ระดับโหลดอะไรเมื่อไหร่Token ที่ใช้
L1name + descriptionตลอดเวลา (ตอน startup)~100 / Skill
L2เนื้อหา SKILL.mdเมื่อ trigger< 5,000
L3+ไฟล์/สคริปต์ประกอบตามการเรียกใช้ผ่าน bashเกือบไม่จำกัด

"ไฟล์ที่ยังไม่ถูกอ่านจะไม่กิน context — จึงไม่มีข้อจำกัดเชิงปฏิบัติของขนาดเนื้อหาที่ bundle ได้"

คุ้มค่าตรงไหน

ถ้าไม่มี Progressive Disclosure

10 Skill × ~5k token ต่อตัว = 50k token หายไปก่อนผู้ใช้พิมพ์อะไรเลย

มี Progressive Disclosure

10 Skill × ~100 token (metadata) = 1k token เท่านั้น โหลดเฉพาะ Skill ที่ตรงงานเข้ามาเต็ม

สคริปต์ยิ่งดีกว่า — โค้ดต้นฉบับไม่เข้า context เลย, เข้าเฉพาะ output

Skill ใช้งานได้ที่ไหน

แพลตฟอร์มPre-builtCustomการแชร์เครือข่าย
Claude API✓ (pptx/xlsx/docx/pdf)✓ ผ่าน /v1/skillsทั้ง workspaceปิด

Beta Headers ของ API

Skill vs MCP vs Subagent

เป็นคำถามที่ต่างกัน ไม่ใช่คำตอบที่ขัดกัน

Skill

ความรู้เชิงขั้นตอนที่ Claude ต้องใช้ ซ้ำๆ

"เราเขียน commit อย่างไร"

MCP

การเชื่อมต่อกับ ระบบภายนอก

"อ่าน Postgres / Slack / GitHub"

Subagent

ผู้ทำงานอิสระ มี context ของตัวเอง

"เปิด code-reviewer agent บน branch นี้"

กรอบการตัดสินใจ (Decision Framework)

ต้องการให้ Claude รู้วิธีทำ X ซ้ำๆ?         → Skill
ต้องการให้ Claude เข้าถึงระบบภายนอก?       → MCP
ต้องการงานที่ทำแยก มี context ของตัวเอง?   → Subagent

"Subagent เรียก Skill ที่ใช้ MCP — คือ pattern ที่ทรงพลังที่สุด"

ตัวอย่างการ Compose

main agent
  └─ subagent: code-reviewer (มี context แยก, tool อ่านอย่างเดียว)
       └─ skill: review-conventions (โหลดตอนใช้งาน)
              └─ MCP: GitHub (ดึง diff + comment ของ PR)

ทุกชั้นมีเหตุผลของตัวเอง — Subagent เพื่อแยก context, Skill เพื่อความรู้, MCP เพื่อเข้าถึงข้อมูล

หลักการเขียน — สี่ข้อสำคัญ

  • กระชับเข้าไว้ — context window คือทรัพย์สินส่วนรวม
  • ถือว่า Claude ฉลาดอยู่แล้ว — เพิ่มเฉพาะสิ่งที่ Claude ยังไม่รู้
  • ปรับ "ระดับอิสระ" ให้เหมาะกับความเปราะบางของงาน
  • ทดสอบกับทุกโมเดล ที่จะใช้ (Haiku/Sonnet/Opus)

"เปรียบเหมือนหุ่นยนต์เดินทาง: สะพานแคบมีหน้าผา → ต้องมีรั้วและคำสั่งชัดเจน. ทุ่งโล่ง → บอกทิศทางพอ"

การตั้งชื่อและคำอธิบาย

ดี

  • processing-pdfs (รูป gerund)
  • analyzing-spreadsheets
  • "Processes Excel files and generates reports. Use when…"

ไม่ดี

  • helper / utils / tools
  • "I can help you with…" (บุรุษที่หนึ่ง)
  • "Helps with documents" (กว้างเกินไป ไม่บอก เมื่อไหร่)

Pattern การ Disclosure ทีละชั้น

  1. Pattern 1 — คู่มือ + อ้างอิง SKILL.md ลิงก์ไปยัง FORMS.md, REFERENCE.md, EXAMPLES.md
  2. Pattern 2 — แยกตามโดเมน เช่น reference/finance.md, reference/sales.md… โหลดเฉพาะที่ถูกถาม
  3. Pattern 3 — รายละเอียดตามเงื่อนไข แสดงพื้นฐาน inline และลิงก์เนื้อหา advanced

กฎเหล็ก: อ้างอิง ลึกแค่ระดับเดียว · ไฟล์ > 100 บรรทัดต้องมี Contents ด้านบน

Workflow + Checklist

## ขั้นตอนการกรอกฟอร์ม PDF

คัดลอก checklist ด้านล่าง แล้วติ๊กตามขั้นตอน:

- [ ] ขั้นที่ 1: วิเคราะห์ฟอร์ม (รัน analyze_form.py)
- [ ] ขั้นที่ 2: สร้าง field mapping (แก้ไข fields.json)
- [ ] ขั้นที่ 3: ตรวจ mapping (รัน validate_fields.py)
- [ ] ขั้นที่ 4: กรอกฟอร์ม (รัน fill_form.py)
- [ ] ขั้นที่ 5: ยืนยันผลลัพธ์ (รัน verify_output.py)

Pattern: plan → validate → execute — ดักจุดผิดก่อนจะเกิด

Evaluation-Driven Development

  1. หาช่องว่าง — รัน Claude บนงานจริง โดยยังไม่มี Skill
  2. เขียน 3 evaluation scenario
  3. วัด baseline
  4. เขียน SKILL.md เท่าที่จำเป็น
  5. วนซ้ำกับ eval

"เขียน Evaluation ก่อนเขียนเอกสารเสมอ"

Loop ปรับ Description

ฟิลด์ description เป็น ปุ่ม trigger เพียงปุ่มเดียว · ปรับมันให้เหมือนปรับโมเดล ML

  1. เตรียม ~20 query: 8-10 ตัว should-trigger, 8-10 ตัว should-not (เน้น near-miss)
  2. แบ่ง train (60%) / validation (40%) ค้างไว้
  3. รันแต่ละ query 3 ครั้ง → คำนวณ trigger rate (ผ่านเมื่อ > 0.5)
  4. ปรับ description ~5 รอบ — แก้เฉพาะที่ฟัน train
  5. เลือกรอบที่ validation ผ่านดีที่สุด ไม่ใช่รอบล่าสุด

Anthropic มี Skill ชื่อ skill-creator ที่ทำ loop นี้ให้อัตโนมัติพร้อม HTML report

Description: ก่อน / หลัง

# ก่อน (แคบเกินไป ไม่บอกว่าเมื่อไหร่)
description: Process CSV files.

# หลัง
description: >
  Analyze CSV and tabular data files — compute summary statistics,
  add derived columns, generate charts, and clean messy data. Use this
  skill when the user has a CSV, TSV, or Excel file and wants to
  explore, transform, or visualize the data, even if they don't
  explicitly mention "CSV" or "analysis."

เจาะจงในส่วน ทำอะไร · กว้างในส่วน เมื่อไหร่ — "Err on the side of being pushy"

Loop "Claude A / Claude B"

Claude A — ผู้เขียน

ช่วยร่างและขัดเกลา Skill — เข้าใจฟอร์แมตในตัว

Claude B — ผู้ใช้

Instance ใหม่ที่โหลด Skill เข้ามา ใช้งานจริงเพื่อเปิดเผยจุดอ่อน

สังเกต Claude B → นำสิ่งที่พบกลับไปบอก Claude A → ปรับปรุง

Claude Code — Superpowers

  • !`git diff HEAD` — Dynamic Context Injection: รันคำสั่งก่อน แล้วเอา output แทรกเข้า prompt
  • context: fork — รัน Skill ใน subagent ที่มี tool ของตัวเอง
  • allowed-tools: Bash(git add *) ... — pre-approve tool ตอน Skill ทำงาน ไม่ต้องกด confirm รายครั้ง
  • disable-model-invocation: true — บังคับให้ เฉพาะผู้ใช้ เท่านั้นที่กดเรียกได้
  • ${CLAUDE_SKILL_DIR} — path ของสคริปต์ portable ไม่ขึ้นกับ CWD

ตัวอย่างจริง #1 — /summarize-changes

---
description: Summarizes uncommitted changes and flags anything risky.
  Use when the user asks what changed, wants a commit message,
  or asks to review their diff.
---

## Current changes
!`git diff HEAD`

## Instructions
สรุปการแก้ไขข้างต้นเป็น 2-3 bullet พร้อมระบุความเสี่ยง
(ขาด error handling, hardcoded values, test ที่ต้อง update)
ถ้า diff ว่าง ให้บอกว่าไม่มีการแก้ไขที่ยังไม่ commit

diff ถูก inline ก่อน Claude อ่าน Skill — ตอบบนข้อมูลจริง ไม่ใช่การเดา

ตัวอย่าง #2 — /deploy ที่ล็อคไว้

---
name: deploy
description: Deploy the application to production
disable-model-invocation: true
allowed-tools: Bash(./scripts/deploy *) Bash(git push *)
---

Deploy $ARGUMENTS to production:
1. Run the test suite
2. Build the application
3. Push to the deployment target
4. Verify the deployment succeeded
  • เฉพาะ ผู้ใช้ เท่านั้นที่ trigger deploy ได้
  • Tool ถูก pre-approve แต่จำกัดเฉพาะที่ระบุ

โมเดลความปลอดภัย (Security Model)

การติดตั้ง Skill = การติดตั้งซอฟต์แวร์ — ต้องระวังเท่ากัน

  • Skill รันใน VM ที่มี filesystem + bash + code execution
  • Skill ที่เป็นภัยอาจ redirect tool, exfiltrate data, ติดตั้ง backdoor
  • ตรวจ ทุกไฟล์ ใน skill: SKILL.md, สคริปต์, asset
  • Skill ที่ดึงข้อมูลจาก URL ภายนอก เสี่ยงเป็นพิเศษ
  • ใช้ disable-model-invocation กับคำสั่งที่มีผลข้างเคียง
  • allowed-tools ของ project skill ทำงานเฉพาะหลัง trust workspace แล้ว

Anti-Patterns ที่ต้องเลี่ยง

  • Path แบบ Windows (scripts\helper.py) — ใช้ forward slash เท่านั้น
  • "Voodoo Constants" — ตัวเลขลึกลับโดยไม่อธิบาย คือบั๊กที่รออยู่
  • "Punt-to-Claude" — แก้ใน script เอง อย่าผลักภาระให้ prompt
  • เสนอทางเลือก 3-4 ทาง — ให้ default 1 ตัว + ทางลงเสริม
  • คำสั่งที่ผูกกับเวลา — ของเก่าให้ย้ายไปส่วน "legacy"
  • ใช้คำไม่สม่ำเสมอ — เลือก 1 คำ ("field" / "endpoint") แล้วใช้คำเดียวตลอด

Checklist คุณภาพของ Skill

คุณภาพหลัก

  • ☐ Description: บุรุษที่สาม, ทำอะไร + เมื่อไหร่, มีคำสำคัญ
  • ☐ SKILL.md body < 500 บรรทัด
  • ☐ อ้างอิงลึกแค่ระดับเดียว
  • ☐ คำศัพท์สม่ำเสมอ
  • ☐ มีตัวอย่างชัดเจน
  • ☐ Workflow มีขั้นตอนชัด

โค้ด & การทดสอบ

  • ☐ สคริปต์จัดการ error เอง
  • ☐ ไม่มี voodoo constant
  • ☐ ใช้ forward slash
  • ☐ มี validation step สำหรับงานสำคัญ
  • ☐ มี eval ≥ 3 + ทดสอบบน Haiku/Sonnet/Opus
  • ☐ รับ feedback จากทีมแล้ว

Playbook สำหรับ Roll-out ในทีม

  1. เลือก workflow หนึ่ง เรื่องที่ทีมต้องอธิบายซ้ำๆ
  2. เขียน 3 evaluation ก่อน เริ่มเขียน SKILL.md
  3. ร่าง SKILL.md ขั้นต่ำ (< 100 บรรทัด)
  4. ลองใช้ส่วนตัว (~/.claude/skills/) วนกับ eval
  5. ย้ายไปที่ project (.claude/skills/) — commit เข้า repo
  6. เก็บข้อมูลการใช้งาน 2 สัปดาห์ — รวบรวม case ที่ล้มเหลว
  7. สรุปบทเรียนเข้าหน้า wiki — ขยายเป็น plugin หากแชร์ทั่วองค์กร
