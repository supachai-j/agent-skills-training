Definition

An Agent Skill is an organised folder of instructions, scripts, and resources that an agent can discover and load dynamically to perform better on a specific task.

  • Entrypoint: SKILL.md (YAML frontmatter + markdown)
  • Optional siblings: scripts/, references/, assets/
  • Open standard at agentskills.io — Apache 2.0 / CC-BY-4.0

An open standard, not just an Anthropic feature

Originally written by Anthropic, released as an open spec, governed via GitHub.

One SKILL.md works across all of these (May 2026, partial):

Anatomy of a Skill

my-skill/
├── SKILL.md            # required — entrypoint
├── reference.md        # loaded only when needed
├── examples.md         # ditto
└── scripts/
    └── helper.py       # executed via bash; source never enters context

Each file has a different "loading time". That timing is the trick.

SKILL.md — minimal example

---
name: pdf-processing
description: Extract text and tables from PDF files, fill forms,
  merge documents. Use when working with PDF files or when the
  user mentions PDFs, forms, or document extraction.
---

# PDF Processing
Use pdfplumber for text extraction:

```python
import pdfplumber
with pdfplumber.open("file.pdf") as pdf:
    text = pdf.pages[0].extract_text()
```

Required: name, description. Everything else is body or supporting files.

Frontmatter — required fields

FieldRule
name≤64 chars · lowercase + digits + hyphens · no leading/trailing - · no -- · must match parent dir
descriptionnon-empty · ≤1024 chars · third person · what + when

Open-standard optional fields:

license · compatibility (≤500 chars, e.g. "Requires Python 3.14+ and uv") · metadata (string→string map) · allowed-tools (experimental)

Claude Code adds extras

On top of the open spec:

when_to_use · argument-hint · arguments · disable-model-invocation · user-invocable · allowed-tools · model · effort · context: fork · agent · hooks · paths · shell

Use them for Claude-Code-specific behaviour. Stick to the open subset for cross-client portability.

Progressive disclosure

The single idea that lets you install hundreds of skills without drowning the context window.

LevelWhat loadsWhenToken cost
L1name + descriptionAlways (startup)~100 / skill
L2SKILL.md bodyWhen triggered< 5,000
L3+Bundled files / scriptsOn demand via bash~unlimited

"Files don't consume context until accessed. There is no practical limit on bundled content."

What that buys you

Without progressive disclosure

10 skills × ~5k tokens each = 50k tokens of instructions before the user even types.

With progressive disclosure

10 skills × ~100 tokens of metadata = 1k tokens. Only the relevant skill's body loads.

Scripts are even better: their source never enters context — only their output.

Skills vs MCP vs Subagents

Different questions, not competing answers.

Skill

Procedural know-how Claude needs repeatably.

"How do we write a commit?"

MCP

Connection to an external system.

"Read this Postgres / Slack / GitHub."

Subagent

Independent worker with own context.

"Spin up a code-review agent on this branch."

Decision framework

Need Claude to know HOW to do X repeatably?    → Skill
Need Claude to ACCESS an external system?       → MCP
Need work done in ISOLATION with own context?   → Subagent

"A subagent can call a skill that uses MCP — that's the most powerful pattern."

Composition example

main agent
  └─ subagent: code-reviewer (own context, read-only tools)
       └─ skill: review-conventions (loaded on demand)
              └─ MCP: GitHub (fetches PR diff + comments)

Each layer earns its existence. Subagent for isolation, skill for know-how, MCP for access.

Authoring — core principles

  • Concise is key. The context window is a public good.
  • Assume Claude is smart. Only add what Claude doesn't already know.
  • Calibrate degrees of freedom to task fragility.
  • Test on every model the skill will run on (Haiku/Sonnet/Opus).

"Robot on a path: narrow bridge with cliffs → tight instructions. Open field → general direction."

Naming and description

Good

  • processing-pdfs (gerund)
  • analyzing-spreadsheets
  • "Processes Excel files and generates reports. Use when…"

Bad

  • helper / utils / tools
  • "I can help you with…" (1st person)
  • "Helps with documents" (vague, no when)

Progressive disclosure patterns

  1. Pattern 1 — Guide + references. SKILL.md links to FORMS.md, REFERENCE.md, EXAMPLES.md.
  2. Pattern 2 — Domain split. reference/finance.md, reference/sales.md… load only what's asked about.
  3. Pattern 3 — Conditional details. Show basics inline, link advanced topics only.

Rule: keep references one level deep. Long files (>100 lines) need a Contents block.

Workflows + checklists

## PDF form filling workflow

Copy this checklist and check off as you complete:

- [ ] Step 1: Analyze the form (run analyze_form.py)
- [ ] Step 2: Create field mapping (edit fields.json)
- [ ] Step 3: Validate mapping (run validate_fields.py)
- [ ] Step 4: Fill the form (run fill_form.py)
- [ ] Step 5: Verify output (run verify_output.py)

Pattern: plan → validate → execute. Catch errors before they happen.

Evaluation-driven development

  1. Identify gaps — run Claude on real tasks without the skill.
  2. Build 3 evaluation scenarios.
  3. Establish baseline.
  4. Write minimal SKILL.md.
  5. Iterate against the evals.

"Create evaluations BEFORE writing extensive documentation."

Description optimization loop

The description is the only trigger. Optimize it like an ML model:

  1. Build ~20 labeled queries: 8-10 should-trigger, 8-10 should-not (near-miss negatives)
  2. Split train (60%) / validation (40%) — keep the split fixed
  3. Run each query 3× → trigger rate (pass > 0.5)
  4. Iterate description ~5 rounds — fix train failures only
  5. Pick the iteration with best validation pass rate (not the latest!)

Anthropic's skill-creator skill automates the whole loop with an HTML report.

Description: before / after

# Before (too narrow, no when-clause)
description: Process CSV files.

# After
description: >
  Analyze CSV and tabular data files — compute summary statistics,
  add derived columns, generate charts, and clean messy data. Use this
  skill when the user has a CSV, TSV, or Excel file and wants to
  explore, transform, or visualize the data, even if they don't
  explicitly mention "CSV" or "analysis."

Specific about what; broad about when. "Err on the side of being pushy."

Claude A / Claude B authoring loop

Claude A — author

Helps you draft and refine the skill. Knows the format natively.

Claude B — user

Fresh instance with the skill loaded. Reveals gaps through real usage.

You observe Claude B → bring findings back to Claude A → repeat.

Claude Code — superpowers

  • !`git diff HEAD` — dynamic context injection before Claude sees the prompt.
  • context: fork — run the skill in a subagent with its own tool set.
  • allowed-tools: Bash(git add *) ... — pre-approve tools, no per-call prompts.
  • disable-model-invocation: true — make a skill user-only for risky actions.
  • ${CLAUDE_SKILL_DIR} — portable script paths regardless of CWD.

Worked example #1 — /summarize-changes

---
description: Summarizes uncommitted changes and flags anything risky.
  Use when the user asks what changed, wants a commit message,
  or asks to review their diff.
---

## Current changes
!`git diff HEAD`

## Instructions
Summarize the changes above in two or three bullet points,
then list risks (missing error handling, hardcoded values,
tests that need updating). If empty, say so.

Diff is inlined before Claude reads the skill — grounded in reality, not guesses.

Worked example #2 — locked-down /deploy

---
name: deploy
description: Deploy the application to production
disable-model-invocation: true
allowed-tools: Bash(./scripts/deploy *) Bash(git push *)
---

Deploy $ARGUMENTS to production:
1. Run the test suite
2. Build the application
3. Push to the deployment target
4. Verify the deployment succeeded
  • Only the user can trigger deploy.
  • Tools are pre-approved, but only those tools.

Worked example #3 — codebase-visualizer

---
name: codebase-visualizer
description: Generate an interactive collapsible tree visualization
  of your codebase. Use when exploring a new repo, understanding
  project structure, or identifying large files.
allowed-tools: Bash(python3 *)
---

python3 ${CLAUDE_SKILL_DIR}/scripts/visualize.py .
  • Bundles a Python script that emits an HTML tree view.
  • Skill is the orchestrator; the script does the work.
  • This pattern works for any visual output: dep graphs, coverage reports, schemas.

Validate before you ship

Use the official reference SDK:

skills-ref validate ./my-skill

Catches:

  • name / parent-directory mismatch
  • Bad characters or length in name / description
  • Malformed YAML
  • Constraints on optional fields (compatibility, metadata)

Also useful as a parser to embed if you're building a Skills client. Repo: github.com/agentskills/agentskills

Security model

Treat installing a Skill like installing software.

  • Skills run in a VM with filesystem + bash + code execution.
  • A malicious skill can redirect tool use, exfiltrate data, install backdoors.
  • Audit every bundled file: SKILL.md, scripts, assets.
  • External-URL fetches inside skills are especially risky.
  • Use disable-model-invocation for any side-effect command.
  • Project skills' allowed-tools only activates after workspace trust.

Anti-patterns to avoid

  • Windows-style paths (scripts\helper.py) — always use forward slashes.
  • "Voodoo constants" — every magic number documented or it's a bug waiting to happen.
  • "Punt-to-Claude" error handling — solve in the script, not in the prompt.
  • Three valid alternatives — give one default + an escape hatch.
  • Time-sensitive instructions — push deprecated content into a "legacy" section.
  • Mixed terminology — pick one term ("field" / "endpoint") and stick with it.

Skill quality checklist

Core quality

  • ☐ Description: third person, what + when, key terms
  • ☐ SKILL.md body < 500 lines
  • ☐ References one level deep
  • ☐ Consistent terminology
  • ☐ Concrete examples
  • ☐ Workflows have clear steps

Code & testing

  • ☐ Scripts handle their own errors
  • ☐ No voodoo constants
  • ☐ Forward-slash paths only
  • ☐ Validation steps for critical ops
  • ☐ ≥3 evals; tested on Haiku/Sonnet/Opus
  • ☐ Team feedback incorporated

Rollout playbook for your team

  1. Pick one repeating workflow your team explains over and over.
  2. Write 3 evaluations before any SKILL.md.
  3. Draft a minimal SKILL.md (lt;100 lines).
  4. Try it personally (~/.claude/skills/); iterate against evals.
  5. Promote to the project (.claude/skills/); commit it.
  6. Run a 2-week observation window — collect failure cases.
  7. Crystallise lessons into the wiki, then expand to a plugin if shared org-wide.
