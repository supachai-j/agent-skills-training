Agent Skills — Technical Deep Dive

A 12-module training on the Agent Skills open standard — what they are, how they load, and how to author, test, secure, and roll them out across a team.

Module 01

Welcome & what you'll learn

A short orientation: why skills exist, what changes when you adopt them, and the path through this course.

Modern coding agents are good at general tasks but routinely lack the specific context they need to do real work reliably — your team's commit conventions, the precise way you fill out a PDF form, the migration runbook your senior engineer keeps in a Notion page. Agent Skills are an open format for capturing that procedural knowledge as a folder of files (one SKILL.md plus optional siblings) that any compatible agent can discover and load on demand.

Once a skill is written, you stop pasting the same instructions every session. Once it's in source control, the whole team gets it. Once it's in .agents/skills/, every conformant agent — Claude Code, Copilot, Cursor, Codex, Gemini CLI, and dozens more — can use it without modification.

What this course covers

  • The technical anatomy of a skill — frontmatter, body, sibling files, validation rules.
  • Progressive disclosure — why skills don't drown your context window and how to author for it.
  • The open standard at agentskills.io and the cross-client convention.
  • The decision framework for Skills vs MCP vs Subagents (you'll need all three).
  • Authoring best practices, with concrete worked examples.
  • A short lab on description optimization — the single most important quality dial.
  • How to implement Skills support in your own client agent.
  • Security model, rollout playbook, and a cheatsheet you can keep.

Time

~45 minutes to read, ~90 minutes if you do the labs.

Module 02

What is an Agent Skill?

A precise, vendor-neutral definition.

An Agent Skill is an organised folder of instructions, scripts, and resources that an agent can discover and load dynamically to perform better on a specific task. The contract has three parts:

  1. A folder whose name is the skill's name.
  2. A SKILL.md file at the folder root, containing YAML frontmatter and markdown.
  3. Optional sibling content in canonical directories: scripts/, references/, assets/.
my-skill/
├── SKILL.md          # required — entrypoint
├── scripts/          # optional — executable code
├── references/       # optional — documentation
├── assets/           # optional — templates, data
└── ...

The standard is intentionally minimal. Two required fields — name and description — plus a markdown body. Everything else is optional or platform-specific.

"Building a skill for an agent is like putting together an onboarding guide for a new hire." — Anthropic Engineering

The analogy holds. A new hire doesn't need to memorise the entire wiki on day one; they need a table of contents and pointers to where the deep material lives. An agent works the same way — it doesn't read every skill end-to-end, only the ones it judges relevant to the current task.

Takeaway

A skill is a folder, not a snippet. The folder layout is what makes progressive disclosure possible.

Module 03

Anatomy: the SKILL.md contract

Frontmatter fields, validation rules, and the body.

Every SKILL.md opens with YAML frontmatter between two --- delimiters:

---
name: pdf-processing
description: Extract text and tables from PDF files, fill forms, merge documents. Use when working with PDF files or when the user mentions PDFs, forms, or document extraction.
---

# PDF Processing
...markdown body...

Required fields (open standard)

FieldConstraint
name1-64 chars · lowercase letters/digits/hyphens · no leading/trailing - · no consecutive -- · must match parent directory name
description1-1024 chars · should describe both what the skill does and when to use it

Optional fields (open standard)

FieldPurpose
licenseLicense name or filename of bundled licence text.
compatibility≤500 chars. Note env requirements: Requires Python 3.14+ and uv.
metadataArbitrary string→string map for client-defined fields (e.g. version, author).
allowed-toolsSpace-separated list of pre-approved tools. Experimental.

Claude Code-specific extras

Claude Code adds fields that only apply when the skill runs inside Claude Code: when_to_use, argument-hint, arguments, disable-model-invocation, user-invocable, model, effort, context: fork, agent, hooks, paths, shell. Use them for client-specific behaviour; stick to the open subset for cross-client portability.

The body

Whatever helps the agent perform the task. Step-by-step instructions, examples, edge cases. There are no format restrictions. Recommended cap: 500 lines — beyond that, split into sibling reference files.

Takeaway

The standard is small on purpose. Master the required fields, then add optional fields only when they earn it.

Module 04

Progressive disclosure

The single design principle that makes skills scale.

If every installed skill loaded its entire body into context at startup, ten skills would burn 50,000 tokens before the user typed anything. Progressive disclosure is the staged-loading model that prevents this. Skills load in three tiers:

TierWhat loadsWhenToken cost
L1 — Metadataname + descriptionAlways (session start)~100 tokens / skill
L2 — InstructionsSKILL.md bodyWhen the agent decides the skill is relevant< 5,000 tokens (recommended)
L3+ — ResourcesFiles under scripts/, references/, assets/On demand via bash / file-readEffectively unbounded

Tier 3 is where the magic compounds. A reference file like references/finance.md consumes zero tokens until the agent opens it. Scripts are even better: their source code never enters context — only their output does. A 2,000-line Python script that emits "OK" costs about three tokens after running.

Authoring implications

  • Keep SKILL.md body under 500 lines. Larger content goes into sibling files.
  • Reference siblings one level deep from SKILL.md. Agents may partial-read transitively-linked files (e.g. head -100), missing important content past line 100.
  • For reference files longer than ~100 lines, include a Contents block at the top. The agent can then jump to the right section.
  • For long-running deterministic operations, prefer a script the agent runs over inline instructions the agent has to follow exactly.

Pattern 1 — guide with references

# PDF Processing

## Quick start
[short inline guidance]

## Advanced features
- Form filling: see [FORMS.md](FORMS.md)
- Reference: see [REFERENCE.md](REFERENCE.md)
- Examples: see [EXAMPLES.md](EXAMPLES.md)

Pattern 2 — domain split

For BigQuery-style skills with multiple datasets, split references by domain so the agent only loads what's asked about:

bigquery-skill/
├── SKILL.md
└── reference/
    ├── finance.md   # revenue, billing
    ├── sales.md     # pipeline, opportunities
    ├── product.md   # adoption, usage
    └── marketing.md # attribution

Takeaway

You can install dozens or hundreds of skills if each one is structured for progressive disclosure. The bottleneck is the description, not the body.

Module 05

An open standard, not just an Anthropic feature

Why your skills are portable, and where the canonical spec lives.

Anthropic invented the SKILL.md format and then released it as an open standard at agentskills.io, governed via a public GitHub repository. The standard defines the format; clients implement loading and execution however suits them.

As of May 2026, the format is supported by an unusually broad cross-vendor ecosystem:

Claude Code · Claude.ai · GitHub Copilot · VS Code · OpenAI Codex · Cursor · Gemini CLI · OpenCode · OpenHands · Goose (Block) · Letta · Roo Code · Mistral Vibe · Snowflake Cortex Code · Databricks Genie · Spring AI · Laravel Boost · Kiro · Factory · Junie (JetBrains) · Amp · Mux · Ona · Workshop · Trae (ByteDance) · Piebald · Pi · Emdash · Qodo · VT Code · Command Code · Agentman · Firebender · Google AI Edge Gallery · nanobot · fast-agent · Autohand

One SKILL.md, written once, runs unchanged in any of those — provided you stay within the open subset of frontmatter fields and don't lean on client-specific extras. That's the whole pitch of an open spec: write once, reuse everywhere.

The cross-client convention: .agents/skills/

The standard doesn't mandate a fixed install location, but the ecosystem has converged on .agents/skills/ as the cross-client path. Conformant clients scan it in addition to their own native location.

ScopeNative (per-client)Cross-client
Project<repo>/.<client>/skills/<repo>/.agents/skills/
User~/.<client>/skills/~/.agents/skills/

Universal precedence rule: project-level overrides user-level. Many newer clients also pragmatically scan .claude/skills/ because so many existing skills already live there.

Takeaway

Place team-shared skills in <repo>/.agents/skills/. Personal ones in ~/.agents/skills/. Reach for client-specific paths only when you genuinely need client-specific frontmatter.

Claude API specifics

Skills run inside the API's code-execution container. You need three beta headers:

anthropic-beta: code-execution-2025-08-25
anthropic-beta: skills-2025-10-02
anthropic-beta: files-api-2025-04-14

Reference a skill by skill_id in the container parameter alongside the code-execution tool. The sandbox has no network and no runtime pip install — only pre-installed packages. Skills are also not covered by Zero-Data-Retention today.

Claude Code specifics

Locations and precedence:

WherePathScope
Enterprisemanaged settingsorg-wide
Personal~/.claude/skills/<name>/SKILL.mdall your projects
Project.claude/skills/<name>/SKILL.mdthis repo
Plugin<plugin>/skills/<name>/SKILL.mdwhere plugin enabled

Precedence: enterprise > personal > project. Plugin skills are namespaced plugin:skill and don't conflict.

Claude Code superpowers

  • !`git diff HEAD` — dynamic context injection: a shell command runs before Claude sees the skill, and its output is inlined.
  • context: fork — runs the skill in a forked subagent with its own tool set and isolated context.
  • allowed-tools — pre-approves tools while the skill is active, skipping per-call confirmation.
  • disable-model-invocation: true — only the user can invoke the skill (use for /deploy, /send-slack).
  • ${CLAUDE_SKILL_DIR} — resolves to the skill's directory, so bundled scripts work regardless of the working directory.

Cross-surface note

Custom skills do not sync across surfaces. Upload separately to API, claude.ai, and Claude Code. The portable thing about skills is the format, not the deployment.

Module 07

Skills vs MCP vs Subagents

Three different questions, not three competing answers.

Newcomers usually try to pick one. Production setups use all three. The trick is knowing what each is good for.

FeatureSkillsPromptsProjectsSubagentsMCP
PurposeProcedural know-howPer-turn instructionsBackground knowledgeTask delegationExternal tool connectivity
PersistenceAcross conversationsOne conversationWithin projectAcross sessionsContinuous
LoadingDynamic, on demandEach turnAlways in projectWhen invokedAlways available
Includes codeYesNoNoYesYes

Decision framework

Need Claude to know HOW to do X repeatably?     → Skill
Need Claude to ACCESS an external system?        → MCP
Need work done in ISOLATION with own context?    → Subagent

Composition (the powerful pattern)

main agent
  └─ subagent: code-reviewer (own context, read-only tools)
       └─ skill: review-conventions (loaded on demand)
              └─ MCP: GitHub (fetches PR diff + comments)

Each layer earns its existence. Subagents isolate context. Skills hold the know-how. MCP fetches the data. The interesting work happens at the interfaces between them.

Takeaway

Don't make this an either/or. The right answer is usually "skill plus MCP, optionally inside a subagent."

Module 08

Authoring best practices

Anthropic's official guidance, distilled.

Four core principles

  1. Concise is key. The context window is a public good. Once SKILL.md loads, every token competes with conversation history.
  2. Assume Claude is smart. Only add what the model doesn't already know. Don't explain what a PDF is.
  3. Calibrate degrees of freedom. Match instruction tightness to task fragility. DB migrations need exact commands; code reviews need general direction.
  4. Test on every model the skill will run on (Haiku, Sonnet, Opus). What works for Opus may need more handholding on Haiku.

Naming

Use gerund form when possible: processing-pdfs, analyzing-spreadsheets, reviewing-pull-requests. Avoid vague names — helper, utils, tools, data — they tell the agent nothing about when to reach for the skill.

Description rules

  • Always third person. "Processes Excel files…", not "I can help…" or "You can use this to…".
  • Always include both what the skill does and when to use it.
  • Imperative phrasing for the trigger half: "Use when the user…".
  • Err on the side of being pushy. List adjacent contexts: "…even if they don't explicitly mention CSV or analysis."

Anti-patterns

  • Windows-style paths (scripts\helper.py). Always use forward slashes.
  • Voodoo constants — every magic number documented or it's a bug waiting to happen.
  • "Punt-to-Claude" error handling — solve in the script, don't shove the problem back into the prompt.
  • Three valid alternatives — give one default and an escape hatch.
  • Time-sensitive instructions — push deprecated content into a "Legacy" section so it doesn't rot the live guidance.

Workflows

For multi-step tasks, give the agent a checklist it can copy into its response and tick off as it goes. Pattern: plan → validate → execute. The validation step catches errors before they become destructive.

## PDF form filling workflow

Copy this checklist:
- [ ] Step 1: Analyze the form (run analyze_form.py)
- [ ] Step 2: Create field mapping (edit fields.json)
- [ ] Step 3: Validate mapping (run validate_fields.py)
- [ ] Step 4: Fill the form (run fill_form.py)
- [ ] Step 5: Verify output (run verify_output.py)

Takeaway

The two highest-leverage things you can fix in any skill are the description (does it activate at the right time?) and the workflow (does it make the task harder to mess up?). Everything else is secondary.

Module 09

Description optimization (lab)

A mini lab: optimize a skill's description like an ML model.

The description is the only field that decides whether a skill activates. An under-specified description means the skill never triggers; an over-broad one means it triggers when it shouldn't. agentskills.io documents a structured loop borrowed from ML evaluation practice.

Step 1 — build a labeled query set

Aim for 20 user-style queries, half should-trigger and half should-not.

[
  { "query": "I've got a spreadsheet in ~/data/q4_results.xlsx with revenue in col C and expenses in col D — can you add a profit margin column and highlight anything under 10%?", "should_trigger": true },
  { "query": "whats the quickest way to convert this json file to yaml", "should_trigger": false }
]

Vary the should-trigger queries on phrasing (formal/casual/typos), explicitness (names the domain vs hides it), detail (terse vs context-heavy), and complexity (one-step vs multi-step).

For should-not queries, the most useful negatives are near-misses — queries that share keywords with your skill but actually need something different. "Write a fibonacci function" is a useless negative; "I need to update the formulas in my Excel budget spreadsheet" is a powerful one for a CSV-analysis skill, because the keywords overlap but the task is Excel editing, not CSV analysis.

Step 2 — split train / validation

Train ~60%, validation ~40%. Keep the split fixed so you're comparing iterations like-for-like. Both sets must contain a proportional mix of positives and negatives.

Step 3 — measure trigger rate

Models are non-deterministic. Run each query 3 times and compute a trigger rate (fraction of runs where the skill activated). A should-trigger query passes if trigger_rate > 0.5; a should-not query passes if trigger_rate < 0.5.

Step 4 — iterate

  1. Evaluate on train + validation.
  2. Identify train failures only.
  3. Revise:
    • Should-trigger failures → broaden scope, add adjacent contexts.
    • Should-not failures → add specificity, mark out-of-scope.
    • Don't paste keywords from failed queries — that's overfitting. Find the underlying category and address that.
    • Stay under 1024 chars.
  4. Repeat ~5 iterations.
  5. Pick the iteration with the best validation pass rate — not the latest one. Earlier iterations sometimes generalise better.

Before / after example

# Before
description: Process CSV files.

# After
description: >
  Analyze CSV and tabular data files — compute summary statistics,
  add derived columns, generate charts, and clean messy data. Use this
  skill when the user has a CSV, TSV, or Excel file and wants to
  explore, transform, or visualize the data, even if they don't
  explicitly mention "CSV" or "analysis."

The "after" is specific about what (summary stats, derived columns, charts, cleaning) and broad about when (CSV/TSV/Excel, even without explicit keywords).

Lab — try it now

Pick any skill in ~/.claude/skills/ (or write a fresh one), build a 20-query labeled set, and run the optimization loop. If you don't want to write the runner from scratch, the skill-creator Skill in anthropics/skills automates the whole loop and emits an HTML report.

Module 10

Implementing a Skills client

If you're building an agent and want to be a conformant Skills client.

This module is for agent builders, not skill authors. agentskills.io publishes the canonical implementation lifecycle — five steps from filesystem scan to context lifecycle.

Step 1 — Discover

Scan project + user (and optionally org/built-in) scopes for subdirectories containing exactly SKILL.md. Always include the cross-client convention .agents/skills/. Consider also scanning .claude/skills/ for compatibility.

Bound the search: max depth 4-6, max ~2,000 directories. Skip .git/, node_modules/. Honour .gitignore. Apply a workspace trust check before loading project-level skills — they live in the repo, which may be untrusted.

Step 2 — Parse

Be lenient. Warn on cosmetic violations (name mismatch, >64 chars), only skip the skill on essentials (missing description, unparseable YAML). Skills authored for other clients sometimes have technically-invalid YAML — most often unquoted colons inside values:

description: Use this skill when: the user asks about PDFs   # invalid YAML

A common fix is to wrap such values in quotes and retry parsing.

Step 3 — Disclose (Tier 1)

Inject a structured catalog into the system prompt or a dedicated tool description:

<available_skills>
  <skill>
    <name>pdf-processing</name>
    <description>Extract PDF text, fill forms, merge files. Use when handling PDFs.</description>
    <location>/home/user/.agents/skills/pdf-processing/SKILL.md</location>
  </skill>
</available_skills>

~50–100 tokens per skill. Hide disabled skills entirely; don't list them and block at activation time.

Step 4 — Activate (Tier 2)

Two patterns: file-read activation (the model reads SKILL.md with its standard read tool) or dedicated activate_skill(name) tool. The latter lets you wrap content in identifying tags, list bundled resources, and enforce permissions.

Constrain the name parameter to the discovered set (enum) so the model can't hallucinate a non-existent skill.

Step 5 — Manage skill context over time

  • Protect skill content from compaction. Losing a skill mid-session silently degrades behaviour without any visible error.
  • Deduplicate activations. Skip re-injection if already in context.
  • Subagent delegation (advanced) — run the skill in a separate session and return only a summary.

Reference SDK

Use skills-ref as your validator and parser. Drop it in CI:

skills-ref validate ./my-skill

Takeaway

Implementing the five-step lifecycle correctly is what makes you a conformant client. The hardest part is context management (step 5) — get it wrong and skills "stop working" silently after the first compaction.

Module 11

Security & rollout playbook

Treat installing a Skill like installing software.

Threat model

  • Malicious instructions can redirect tool use away from the stated purpose.
  • Bundled scripts can exfiltrate data or attack the host.
  • External-URL fetches inside skills can be tampered with after installation.
  • A skill with broad allowed-tools quietly raises the trust boundary.

Mitigations

  • Install only from trusted sources — Anthropic-published or org-internal.
  • Audit every bundled file: SKILL.md, references, scripts, assets.
  • Be especially suspicious of skills that fetch external URLs at runtime.
  • In Claude Code, project skills' allowed-tools only activates after workspace trust is granted.
  • Use disable-model-invocation: true for any side-effect command (/deploy, /send-slack) so the trigger stays human.
  • The Claude API has no network — partial mitigation against exfiltration. claude.ai's network is admin-policy-controlled.

Team rollout playbook

  1. Pick one repeating workflow your team explains over and over.
  2. Write 3 evaluations before you write the SKILL.md.
  3. Draft a minimal SKILL.md (under 100 lines).
  4. Use it personally first (~/.claude/skills/ or ~/.agents/skills/); iterate against the evals.
  5. Promote to the project (.claude/skills/ or .agents/skills/); commit it.
  6. Run a 2-week observation window. Collect failure cases.
  7. Crystallise lessons into the wiki. Expand to a plugin if it should be shared org-wide.

Note on ZDR

Skills are not covered by Zero-Data-Retention agreements as of May 2026. Don't put highly sensitive procedural knowledge into a Skill that runs on a non-self-hosted surface.

Cheatsheet & resources

A one-screen quality checklist plus links you'll want again.

Skill quality checklist

Core quality

  • ☐ Description: third person, what + when, key terms, <1024 chars
  • ☐ name matches parent directory and obeys naming rules
  • ☐ SKILL.md body < 500 lines
  • ☐ Sibling references one level deep
  • ☐ Reference files >100 lines have a Contents block
  • ☐ Consistent terminology throughout
  • ☐ Concrete examples, not abstract handwaving
  • ☐ Workflows have clear, numbered steps
  • ☐ Time-sensitive content moved to a Legacy section

Code & scripts

  • ☐ Scripts handle their own errors; no "punt to Claude"
  • ☐ No voodoo constants — every magic number documented
  • ☐ Forward-slash paths only
  • ☐ Required packages listed and verified available in the runtime
  • ☐ Validation step for any destructive operation
  • ☐ Plan-validate-execute pattern for batch operations

Testing

  • ☐ ≥3 evaluations covering the original capability gap
  • ☐ Description optimized with train/validation split
  • ☐ Tested on Haiku / Sonnet / Opus
  • ☐ Validated by skills-ref validate
  • ☐ Team feedback incorporated
